## 2. LLM response

I cloned the repo to look at the structure, and it's in very good shape for a port. Of the roughly 11,000 lines, about 4,000 are a pure, toolkit-independent core (`workspace.py`, `bibtex.py`, the APA 7 and ACIS formatters, `csl.py`, `catalogue_sort.py`, etc.), and the GTK 3 and GTK 4 front-ends are each around 3,500 lines sitting on top of it. The most important design decision, though, is that the files on disk *are* the database: one `.bib` and one `.md` per record, sharded by letter, plus YAML for authors, outlets and works. That on-disk format is the real contract, which means a Mac app doesn't have to share any code with the Python version at all. It only has to read and write the same workspace. You could run the GTK version on Linux and a Mac version on your laptop against the same Syncthing or Git folder.

### The signing situation, since it shapes everything

For running the app on your own Mac, you need no account of any kind. Xcode is free, and you can set the signing to "Sign to Run Locally" (ad-hoc signing). Apple Silicon requires native code to carry a signature, but an ad-hoc one satisfies that, and apps you build yourself aren't quarantined, so Gatekeeper leaves them alone.

The $99 program only matters for distribution to other people. It's what gets you a Developer ID certificate, notarization, and the Mac App Store, plus entitlements like CloudKit. Without it, a colleague who downloads your `.app` gets blocked on first launch and has to go to System Settings → Privacy & Security → Open Anyway (recent macOS versions removed the old Control-click shortcut), or run `xattr -dr com.apple.quarantine` on it. Homebrew is no longer an escape hatch either: Homebrew announced it is ending support for all casks that fail Gatekeeper checks on September 1st, 2026, and it is deprecating the --no-quarantine flag, which was used to run unsigned/unnotarized applications. So for sharing, your realistic options are "Open Anyway" instructions in the README, or having people build from source.

The good news is that this app needs nothing that requires a paid account. It doesn't need iCloud entitlements because users can just put the workspace folder in iCloud Drive, Dropbox or Syncthing. And it doesn't need the sandbox, which is only mandatory for the App Store.

### Option 1: SwiftUI rewrite (most native, my recommendation)

This gets you the most genuinely Mac-feeling result, and the app's structure maps onto SwiftUI unusually well. The three-pane Catalogue is exactly what `NavigationSplitView` is for. SwiftUI's `Table` takes an array of sort comparators, which gives you multi-key sorting (Year descending, then Author) essentially for free, with native clickable column headers. Right-click menus are `.contextMenu`, Preferences becomes a standard `Settings` scene, and the menubar becomes `Commands`.

Porting the core is the main work, but it's the easy kind of work, because it's string processing with no UI. The BibTeX fallback parser (brace-balancing) and the APA 7 and ACIS formatters translate to Swift fairly mechanically. Yams handles YAML frontmatter. The one hard piece is CSL, since there's no mature Swift citeproc. The pragmatic answer is to run citeproc-js (the engine Zotero uses) inside JavaScriptCore, which ships with macOS. Alternatively, you could launch with only the built-in APA and ACIS styles and add CSL later.

For the notes pane, I'd wrap an `NSTextView` rather than relying on SwiftUI's `TextEditor`. You'd then port the regex Markdown highlighter to an `NSTextStorage` delegate, which is the standard AppKit pattern and performs well. Rich-text reference copying writes RTF and HTML to `NSPasteboard` alongside plain text.

Given that the repo has a `vibe-coding` folder and a MAINTENANCE.md explicitly written for "a developer (human or AI)," this is also a very tractable AI-assisted port. You could hand an agent the pure modules one at a time along with the workspace spec.

### Option 2: Swift UI on top of the existing Python core

You keep the Python core, including citeproc-py, and write only the front-end in SwiftUI. There are two ways to connect them. You can embed a Python framework in the app bundle (BeeWare's Python-Apple-support project provides one) and call into it with PythonKit. Or you can run the core as a subprocess speaking JSON over stdin/stdout. The subprocess approach is simpler and keeps the boundary clean.

The tradeoffs are a larger app (tens of MB for the bundled interpreter), every nested `.so` needing to be signed (ad-hoc is fine), and two languages to maintain. With a core this small and this cleanly written, I think a straight port ends up less total effort. But this option is worth it if you want Linux and Mac to share one source of truth for citation formatting.

### Option 3: Stay in Python, use native Cocoa widgets

This fits if you'd rather not learn Swift.

**Toga** (BeeWare) is interesting here because it has both a Cocoa backend and a GTK backend. A single Toga UI would give you real `NSTableView`s and native windows on the Mac, and could in principle replace both GTK front-ends on Linux. The catch is that Toga's widget set is deliberately lowest-common-denominator. Multi-key sortable tables, a syntax-highlighted editor, and a filter sidebar with counts would each push you into platform-specific workarounds.

**PyObjC** gives you the full AppKit API from Python, so nothing is out of reach. The cost is that you're writing verbose Objective-C-shaped code, with thin documentation and no access to SwiftUI.

Either way, Briefcase packages the result as a proper `.app` and has an ad-hoc signing option for local use.

### What won't meet the "feels native" bar

GTK itself does run on macOS via Homebrew, so the current app could be packaged as-is. But it will look like a GNOME app, with libadwaita styling, non-Mac keyboard behaviour, and no proper menubar integration. Qt (PySide6) is better at blending in but still has an uncanny-valley quality in text fields, sidebars and preferences. Electron and Tauri are further still. All of these are fine if "runs on Mac" is the goal, but not if "feels like a Mac app" is.

### A few Mac-specific ideas for the redesign

If you go with option 1, some things are worth adapting rather than translating literally:

- **Fold the tabs into the sidebar.** The GTK notebook tabs (Catalogue, Authors, Outlets, DOI, My Works) would feel more Mac-like as sections of the sidebar source list, the way Mail or Music organise things.
- **DOI lookup as search.** It could become a toolbar search field.
- **Quick Look for full-texts.** Pressing Space on a record to preview the attached PDF is a small feature that makes the app feel native immediately.
- **Drag-and-drop import.** Dropping `.bib` files onto the window is the natural import gesture on a Mac.
- **Live refresh.** Since your design already says any external change is recoverable by rescanning, watching the workspace with FSEvents would let the app refresh when Syncthing or Git changes files underneath it.
